# A trigger is the CLI's injection record or a confirmed read of the skill

A trigger is a trial's evidence that the skill's text reached the model, on both agents: the CLI's own record that it injected the skill (a `Skill` call whose result is not an error, Claude Code's record of a slash command's expansion, or Codex's `explicit` event), or a read of the skill's `SKILL.md` that the trace confirms. Nothing that rests on the prompt's text alone counts. A by-name-only skill made this necessary: no agent loads it with a `Skill` call, so on Claude Code the old rule could not score a by-name invocation, and a prompt that asks for the skill shows only that it was asked for, not that it loaded.

On Claude Code, `claude -p "/<name> <request>"` injects the skill's text into the first request, but neither the stream-json transcript nor the debug log shows it. The only local record is the session file: a `user` record with `isMeta: true` whose text starts `Base directory for this skill: <path>`, written before the model replies. Text a tool prints lands in a `tool_result`, never in such a record. So the agent's runs keep session persistence on, in both arms, and after each run the adapter reduces the file to a line naming its session and one line per expansion, and never stores it. Against the fake API, persistence changed no request but `metadata.user_id`, whose ids differ between any two trials anyway. A run without its own session's record fails closed as an infrastructure error, so a missing file, another session's file and a session with no expansion are three outcomes. The grader keeps persistence off. The file sits in the trial home, which the agent's Bash tool can write, so an agent could in principle rewrite it; this limit is stated, not mitigated.

A confirmed read now counts on Claude Code as it already did on Codex: a `Read` of the installed copy's `SKILL.md` with a result that is not an error, or a Bash command that passes Codex's read rule, which moved unchanged into a module both adapters share. Without it, a `should_trigger: false` case passed on Claude Code even when the agent read the skill in the most direct way there is. The rule confirms only a reader program run last, after nothing but `cd` and `pwd` joined by `&&`, with no redirection or help flag, a successful result and output beyond the `pwd`s. So a trigger is a lower bound on loads: a pipe, `awk`, an interpreter, Claude Code's `Grep` tool or a copy read under another name can show the agent the skill's text and record no trigger, a quiet case's pass means no confirmed load, and quiet cases' transcripts are read by hand at each live run. One exception runs the other way: `sed` is a reader whatever its script, so `sed -n = SKILL.md` counts although it printed none of the skill's text. A trigger is evidence of a load, not proof. Codex's rule and cowsay's recorded results do not change.

## Considered options

- **The CLI's command list plus the by-name prompt.** `init.slash_commands` shows that the command existed and the prompt that it was asked for, not that the skill was injected: a trigger resting on the prompt's text.
- **`--input-format stream-json --replay-user-messages`.** It replays only the `<command-name>` text, not the skill's body, and would move every trial's prompt from an argument to stdin.
- **Tightening the `sed` test**, so only a script that prints the file counts. Not taken: it would change the read rule on both agents, so the rule is kept as it is and the limit stated instead.
- **Leaving Claude Code's `Read` uncounted.** A quiet case would pass on a trial whose agent read the skill, which contradicts "a trial where the agent loads the skill anyway fails the case".
